#### P0-2. CI analytics run on an empty database every day; the extraction backlog is silently dropped
`.github/workflows/scraper_cron.yml:25-31, 63-68`, `src/storage/db.py:21`, `src/extractor/llm_extractor.py:252-253`
Root cause: the workflow caches only `data/seen_jobs.json`. `data/market.db` is gitignored and recreated on every runner, but the full pipeline reads its extraction queue and its market report from that **local** file. Consequences in production:
1. Each run extracts at most 10 of that day's jobs. Every job not reached that day is never extracted, because tomorrow's `market.db` does not contain it. Turso (`jobs`) grows by hundreds per day; `skills_extracted` by 10.
2. The queue is `ORDER BY created_at ASC` over rows inserted in the same second, so it is insertion order: first keyword first. Keyword 2 (`data engineer`) is systematically under-sampled.
3. The Telegram brief ("Analyzed N active tech job postings") and the blueprint's "dominant stack" are computed from at most ~30 rows, including the `Non-Tech` placeholders (see P1-9).

Lazy fix that holds: persist `market.db` with its **own** cache pair. Do not add it to the existing `path:` list: the cache version hashes the path set, so changing it orphans the current `seen_jobs` entry and the next run re-alerts up to 3 days of jobs.

+          path: data/market.db
+          key: market-db-v1-${{ github.run_id }}

+            market-db-v1-
 ...

         ...

#### P0-3. No request timeout and no cross-call circuit breaker on Gemini; a 503 storm overruns the 10-minute job
`src/extractor/gemini_client.py:121`, `src/extractor/llm_extractor.py:144-232`, `src/generator/ideation_engine.py:84-160`, `gemini_filter.py:112`, `main.py:294-295`
Root cause:
- `genai.Client(api_key=...)` has no `http_options` timeout, so one hung request blocks until the job is killed.
- Retries reset per job. Under sustained 503s each job costs about 5+10+20 s of backoff plus jitter and 4 round trips (~42 s). `process_unprocessed_jobs` fetches `limit * 3 = 30` candidates and keeps going while `success_count < 10`, so the worst case is ~30 x 42 s ≈ 21 min against `timeout-minutes: 10`.
- When the runner kills the job, ideation, export and the market brief never run. Dedupe state is saved only in `finally`, so it depends on the cancel signal reaching Python through `bash -el` before SIGKILL. If it doesn't, tomorrow re-sends every alert already sent today.
- The retry block is copy-pasted in both services, the shared helpers `is_transient_error` / `calculate_backoff_sleep` are imported but unused, and the 503 fallback only triggers when the model string is literally `"gemini-3.8-flash"`. Set `GEMINI_MODEL` to anything else and the fallback never fires.

## 3. Feature roadmap (ranked by portfolio ROI)

1. **Full-JD ingestion plus an extraction eval harness.** Fetch the job detail for each new listing (one request per *new* job; dedupe already exists), then hand-label ~50 JDs as a golden set and add `python -m jhunt.eval`, which reports per-field precision and recall for `ExtractedJob` and runs in CI on prompt or model changes. This fixes P1-14 and turns "I called an LLM" into "I measured an LLM pipeline and caught a regression when the model changed", which is the strongest signal on this list for any AI-adjacent role.
2. **Skill demand over time, with salary.** Add a `skill_weekly(week, skill, role, postings)` rollup written by the pipeline, and parse `salaryLabel` (present on ~25% of ads) into a THB range. The analytics page then shows real deltas ("Go postings +38% over 12 weeks; median advertised salary for Go + Kafka roles"). Every number traces to a row, which is the opposite of P0-1.
3. **One store: Turso as the system of record.** Add `alerted_at` and `extracted_at` columns to `jobs`, drive dedupe, the extraction queue, and the analysis from Turso, and delete `seen_jobs.json`, the local `market.db`, both cache pairs, and `StateManager`'s persistence. That removes P0-2, P1-12, and P2-11 at the root and makes the CI job stateless. Pair it with the `libsql-client` deprecation migration.
4. **Read-only public API and feeds.** `GET /api/skills?role=backend&weeks=12` and `GET /api/blueprints` as route handlers with `Cache-Control: s-maxage=3600`, plus `/blueprints/feed.xml`. Small, testable, and shows API design (versioning, pagination, caching headers) on real data.
5. **Full-text job search.** An FTS index over `jobs(title, company, teaser)` in libSQL, with a `/jobs?q=go+kafka+bangkok` page. Useful to you daily, and shows search indexing. Lower ROI than 1-4 because it is common in portfolios.

Not recommended: the "repo scaffold generator from a blueprint". The blueprints are templated (slop item 8), so scaffolding them multiplies template output. Do #1 first, and revisit once specs carry real, distinct content.
